  <name>Task 10: Stop double-encoding document_content into rag_pill task field</name>
  <files>backend/tool_arena/client.py</files>
  <change>
    Production logs (2026-05-13 09:40:47) showed `qa_broad/langchain` failing on a 508 KB doc with OpenRouter 400: "maximum context length is 131072 tokens. However, you requested about 147325 tokens (143229 of text input...)". With `top_k=8 × chunk_size=800 = 6400` chars of retrieved context, the prompt should have been ~2000 tokens — but the LLM was being fed ~570 KB of input.

    Root cause: `single_mcp_call` was prepending the FULL document inside the `task` field as a `[CONTEXT]\n{doc}\n[/CONTEXT]\n\n{task}` block (via `_build_task_prompt`), AND passing `document_content` as a separate kwarg. rag_pill's `render_prompt()` lays the task verbatim under "Question:", so the full doc landed inline next to the retrieved chunks. Past ~400 KB the prompt busted the model's 131072-token context window.

    Fix: only the `call_agent` path (Clarifeye, no separate document_content field) keeps the embedded format. The rag_pill_query branch now passes the raw `task` and lets the dedicated `document_content` parameter carry the doc. Equifinality contract preserved — Tool A and Tool B still see the same `(task, goal, document_content)` tuple, just without the double-encoding.
  </change>

<follow_ups>
## Open architectural follow-up

The batched_embed cost-amplification fix (Task 8) only helps **txtai** because that's the one engine routing through `batched_embed`. The other four engines hand their embedder objects to library code (haystack's `OpenAIDocumentEmbedder`, langchain's `OpenAIEmbeddings`, llamaindex's `OpenAILikeEmbedding`, chromadb's `OpenAIEmbeddingFunction`) — each library does its own internal batching with no shared cache.

To extend the same resumability to those engines, every engine's embedder seam would have to be routed through a single shared callable. Candidate skill to run: `/improve-codebase-architecture` against `mcp_servers/rag_pill/engines/` looking for the "5 embedder seams → 1 embedder seam" deepening opportunity.

Not blocking — txtai is the engine that surfaced the 428KB-doc bug. Other engines may have similar latent behavior on very large docs but no production report yet.
</follow_ups>
